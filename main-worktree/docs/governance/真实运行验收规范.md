# 真实运行验收规范

- 规则编号：`REAL-RUNTIME-ACCEPTANCE-001`
- 生效版本：`V1.14.2.8.4.27.2.36`
- 上位规范：`01-开发治理总纲/PCE-ERP开发治理总纲.md`
- 适用范围：PCE-ERP全部含页面、路由、可运行入口、交互或可视结果的开发、修复、重构和验收任务
- 状态：长期有效

## 1. 真实运行验收优先原则

代码通过不等于系统通过，自动测试通过不等于页面真实可用。自动验收与浏览器人工验收分别证明不同事实，二者不得相互替代：

```text
静态/自动证据 -> 证明规则可重复检查
真实浏览器证据 -> 证明用户从真实URL可见、可读、可操作
Build证据 -> 证明工程可构建
三者共同通过 -> 允许READY
```

脚本读取源码、组件快照、Provider直调、模拟DOM、测试夹具和历史截图都不能替代本次真实浏览器会话。

## 2. 浏览器人工验收强制要求

人工验收必须在真实浏览器中直接打开任务声明URL，等待真实Runtime与Provider完成渲染，并从当前DOM读取用户可见内容。不得只检查源码、接口响应、自动化日志或上一版本页面。

每个被新增、修改、替换、复用影响或明确列为重点验证的页面都必须单独验收。至少检查：

- 最终URL与路由参数；
- 浏览器标题和页面可见标题；
- 顶部区域：页面身份、说明、主操作；
- 中部区域：核心字段、筛选、表格或详情；
- 底部区域：分页、汇总、流程或补充操作；
- 用户可见字段名称与实际值；
- 用户可见按钮名称、可见性和适用的真实点击结果；
- 期望结果与实际结果逐项对照；
- 业务对象与业务写入边界。

不存在某一区域、字段或按钮时，必须记录`N/A`及原因，禁止留空。

## 3. 单页验收记录模板

每页必须使用以下模板，字段不得删减：

```text
Page URL / 页面URL：<最终真实URL>
Page Title / 页面标题：<浏览器标题 / 页面可见标题>
Route Component：<当前路由组件>
Acceptance Regions / 验收区域：
  Top Region / 顶部区域：<稳定标识与实际内容>
  Middle Region / 中部区域：<稳定标识与实际内容>
  Bottom Region / 底部区域：<稳定标识与实际内容>
Checked Fields / 检查字段：<用户可见字段名称和值/来源>
Checked Buttons / 检查按钮：<用户可见按钮名称与动作；无则N/A+原因>
Expected Result / 期望结果：<需求期望>
Actual Result / 实际结果：<真实DOM和动作结果>
Screenshot / 截图：<本次会话证据路径>
Business Write Count：<number>
Page Acceptance：PASS/FAIL/UNKNOWN
```

## 4. 截图证据

每页至少保存一张本次会话截图。单张无法同时证明页面身份、关键区域和动作结果时必须分段截图。截图文件名必须包含版本、页面或业务键、序号；报告必须使用相对仓库路径引用。

页面任务默认归档到`frontend/test-results/<version>/`。治理-only版本用于验证门禁模板的示范截图可以归档到`docs/governance/evidence/<version>/`。截图必须与文字证据来自同一次验收，不得复用历史版本截图冒充本次证据。

## 5. 失败与反向闭环

人工验收出现页面打不开、标题或路由错误、区域缺失、字段不符、按钮不可用、动作无可观察结果、数据来源错误、截图缺失或业务写入越界时，`Browser Human Acceptance=FAIL`。证据不足时为`UNKNOWN`。

`FAIL`或`UNKNOWN`必须阻断READY。若自动验收已PASS而人工验收FAIL，状态固定为`AUTO_PASS_HUMAN_FAIL`，并执行：

```text
登记案例 -> 定位真实运行链根因 -> 判断/完善规范
-> 补强自动验收 -> 重新Build -> 重新浏览器验收
```

禁止修改报告文字、降低期望、引用历史截图或将人工失败改为N/A来规避门禁。

## 6. 三重READY门禁

最终状态必须显式输出：

| 门禁 | PASS条件 | 阻断条件 |
|---|---|---|
| Automatic Acceptance | 所有适用自动检查均PASS | 任一FAIL/UNKNOWN/未执行 |
| Browser Human Acceptance | 所有适用页面均有完整记录和截图且PASS | 任一页面FAIL/UNKNOWN/缺证据 |
| Build | 任务规定的正式Build成功 | 构建失败或未执行 |

判定公式：

```text
Ready Gate =
  Automatic Acceptance == PASS
  AND Browser Human Acceptance == PASS
  AND Build == PASS
```

只有`Ready Gate=PASS`时可以输出`*_READY`。任何历史版本PASS都不能替代当前版本门禁。

## 7. 自动治理检查

- `HUMAN-ACCEPTANCE-REQUIRED-001`：检查版本报告是否包含真实浏览器人工验收章节、逐页状态和截图引用。
- `PAGE-EVIDENCE-001`：检查每页是否记录URL、页面标题、顶部/中部/底部区域、字段、按钮、期望、实际结果及截图。
- `READY-GATE-001`：检查READY是否严格由自动验收、浏览器人工验收和Build三个当前版本结果共同决定。

上述自动检查只验证证据结构与门禁逻辑，不能替代真实浏览器人工验收本身。

## 8. 与现有规范关系

本规范统一`PAGE-RUNTIME-001`、`REQUIREMENT-COMPLETENESS-001`、`CODEX-EVIDENCE-001`与`CODEX-COMMAND-002`的最终READY判定，不替代它们对路由、Runtime、Provider、业务对象、真实点击和页面重构的专项要求。页面重构还必须证明旧Renderer不再承接真实Route。

## 9. 人工验收权限与同对象门禁

从 `V1.14.2.8.4.27.2.45.6` 起，验收状态拆分如下：

```text
Browser Automatic Acceptance: PASS/FAIL
Real Browser Evidence: PASS/FAIL
Human Acceptance: PASS/FAIL/WAITING
```

`Human Acceptance: PASS` 只能由用户明确反馈“人工验收通过”后记录。Codex 打开真实浏览器、执行 Playwright、点击页面并截图仍属于自动验收；用户未签发时必须为 `WAITING`。旧字段 `Browser Human Acceptance` 不得再由自动化签发。

`SAME-OBJECT-ACCEPTANCE-001` 要求逐对象保存自动测试、Runtime、API、页面、点击及归档来源 ID。只显示业务编号但未暴露底层 `SupplierQuotation ID`、使用 Server Memory 投影、点击集合与自动集合不同，均不能判定同对象 PASS。自动 PASS 而人工 FAIL 时，先执行 `RUNTIME-BEFORE-TEST-001`，按页面、API、Runtime、Service、数据库还原对象集合，不得新增对象掩盖差异。

三重 READY 门禁中的人工项以 `Human Acceptance` 为准；其为 `WAITING` 时禁止 READY，即使 Browser Automatic Acceptance、Real Browser Evidence 与 Build 均 PASS。

## 10. 价格归档同对象与税率验收

采购核价与有效价格验收必须输出逐条对账：核价准备 ID、来源类型、来源对象 ID、正式报价 ID、报价明细身份、核价结果 ID、有效价格 ID、可归档判断及阻断原因。核价完成数量不得作为有效价格数量的替代证据。

税率验收必须同时验证配置来源、归档继承顺序、标准选项、维护权限和审计字段。服务热更新或重启导致 Server Memory 价格消失时，必须按当前真实数量报告，不得通过重放确认或直接插入恢复验收基线。

## 11. 决策事实同对象验收（V1.14.2.8.4.27.2.45.8）

`SAME-OBJECT-ACCEPTANCE-002` 验证 `PriceApprovalPreparation -> PriceApprovalResult -> SupplierMaterialPrice.priceApprovalResult` 的同一身份，并同时校验 `originalSourceType/originalSourceReference` 回溯原始事实。验收必须通过页面显式点击形成对象，再验证页面刷新、前端重载及后端重启后仍存在；测试数据库或事务回滚用于自动测试，不得以自动验收污染真实业务数据。

## 12. 持久化四层闭环（V1.14.2.8.4.27.2.45.9）

持久化验收必须逐层记录数据库表和连接、Runtime QuerySet、API 返回行、浏览器渲染行以及相同业务 ID。`Database = Runtime = API = Browser` 四层任一不一致时，持久化为 FAIL。页面运行契约解析失败导致的空表不得归因于缓存，必须保留实际异常字段和接口返回证据。页内刷新必须形成新的 API 请求并更新列表状态，禁止用 `window.location.reload()` 代替。
# LIST-REFRESH-CONTRACT-001 列表刷新真实验收（V1.14.2.8.4.27.2.45.10）

任何页面存在刷新按钮时，人工验收必须实际点击。证据固定为：`Before Data（刷新前数据） != Server New State（服务端新状态）`，点击刷新后 `After Data（刷新后数据） = Server New State`。必须同时证明新API/Runtime请求、行替换、结果数更新以及筛选、排序、pageSize保留；否则 Refresh Acceptance 为 FAIL。禁止用浏览器整体刷新代替。

## 13. 编辑持久化真实验收（V1.14.2.8.4.27.2.45.12）

`PCE-EDIT-PERSISTENCE-001` 要求固定同一业务对象，记录保存请求 Method（方法）、URL、Payload（请求数据）、HTTP Status（状态码）和 Response（响应），并逐层核对数据库、API、Runtime 与浏览器回显。修改原因必须进入正式审计事实；保存后必须依次验证服务端重新读取、页内刷新、浏览器重新加载和后端重启。自动脚本和当前浏览器自动操作不能代替用户最终人工验收。
