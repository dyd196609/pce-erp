# 页面真实运行验收规范

- 规则编号：`PAGE-RUNTIME-001`
- 生效版本：`V1.14.2.8.4.27.2.36`
- 适用范围：全部可访问PCE-ERP业务页面
- 状态：长期有效

## 1. 目的

页面验收必须证明真实运行链成立，不得以文件存在、源码字符串、扫描结果或构建成功替代用户实际可访问和可操作的页面证据。

## 2. 完整运行链

```text
Router
↓
Route Component
↓
Page Runtime
↓
Data Provider
↓
UI Render
↓
User Action
↓
Result
```

任一环节缺失、指向旧实现、读取第二事实源或无法产生声明结果时，`PAGE-RUNTIME-001`为FAIL。

## 3. 三级验收

### Level 1：代码存在验证

验证Router、Route Component、Runtime、Provider绑定、区域、字段、按钮与Action Handler存在，并记录文件和稳定标识。Level 1只能证明实现资产存在，不能单独签发READY。

### Level 2：真实URL运行验证

使用真实浏览器打开目标URL，记录最终URL、页面标题、Route Component、关键区域、关键字段和当前业务对象。必须证明页面无错误、未跳转到旧入口、未渲染旧组件，且入口对象与页面对象一致。

### Level 3：用户操作验证

在真实页面点击任务声明的按钮或控件，记录操作前状态、操作、处理链和可观察结果。刷新、打印、导出等只读动作必须证明页面对象保持且业务写入为0；业务动作必须继续遵守Action与Guard。

## 4. 运行证据

每页至少输出：

```text
Runtime Evidence:
URL: <真实URL>
Page Title: <页面标题>
Route Component: <组件>
Runtime Render: PASS/FAIL
区域: PASS/FAIL
字段: PASS/FAIL
按钮: PASS/FAIL
Action Result: PASS/FAIL
Business Object Before/After: <业务键>
Business Write Count: <number>
Expected Result: <期望结果>
Actual Result: <实际结果>
Screenshot: <证据文件路径>
```

每页必须覆盖顶部、中部、底部三个可见区域；不存在某区域时记录`N/A`及页面结构原因。字段和按钮必须写出用户可见名称，不得只记录CSS选择器。截图必须来自本次真实浏览器会话并包含足以识别页面标题、验收区域和结果的画面，归档到`frontend/test-results`；治理-only版本可归档到`docs/governance/evidence/<version>`。缺少Level 2、适用的Level 3或截图证据时结果为UNKNOWN并阻断READY。

本规范是《真实运行验收规范》的页面专项细化。发生冲突时执行能够提供更完整真实证据、且更严格阻断READY的条款。

## 5. 刷新专项

页面内刷新必须执行`Refresh Button → reloadPageData() → Provider Reload → State Update → UI Refresh`。禁止以`window.location.reload()`、`router.go(0)`或页面跳转代替数据刷新。验收必须比较刷新前后URL、业务对象、Provider加载次数、UI更新标识及业务写入数。

## 6. 与既有规范关系

本规范细化`PROCESS-009`、`PROCESS-011`、`CODEX-COMMAND-002`和`PAGE-RUNTIME-FREEZE-001`的真实运行证据，不降低身份、数据、权限、人工数据保护和冻结资产要求。

## 7. PURCHASE-ORDER-DETAIL-RUNTIME-002 采购订单详情真实运行检查

采购订单详情必须在真实`#/scm/purchase-order/{id}`验证页面标题、采购订单分类、订单编号卡片、基础信息、来源关系、宽表物料明细、生命周期和操作区域。打印输出分类与刷新必须完成真实点击；源码存在或旧组件内存在同名文本不得作为PASS证据。

刷新证据必须记录Provider加载计数和带毫秒的数据更新时间均发生变化，同时URL及订单业务编号保持、业务写入为0。

## 8. REFRESH-RUNTIME-002 真实数据重读检查

详情页刷新必须执行`Refresh Button → Detail Runtime → reloadPageData() → 事实Provider重新读取 → 当前对象更新 → 子项按父身份重新过滤 → UI重新渲染`。验收证据必须包含每次读取的独立执行标识、Provider执行时间、源子项数量、当前对象子项数量和过滤后数量。仅更新时间变化、仅计数器变化或复用上一轮页面缓存均为FAIL。

## 9. PURCHASE-ORDER-ITEM-SOURCE-001 采购订单明细父身份隔离

采购订单详情只能渲染父身份严格等于当前`PurchaseOrder.id`的`PurchaseOrderItem`。兼容既有持久字段`poId`时，若同一行声明多个父订单身份且不一致必须拒绝；父身份缺失的缓存行、测试行和其他订单行不得进入详情或打印。验收必须记录当前PurchaseOrderItem数量与严格过滤后数量。

## 10. PRINT-BUSINESS-CLASSIFICATION-001 采购订单打印业务用途

采购订单打印分类必须使用企业用途：采购员使用、仓库使用、供应商使用、财务留档、管理查看，默认采购员使用。切换用途后预览字段必须按用途真实变化；技术模板码不得作为业务用户标签。
