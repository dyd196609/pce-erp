# PCE-ERP架构与运行边界规范

# 文档信息

- 版本：V1.14.2.8.4.27.1.4.7
- 用途：统一Page、Schema、Provider、Runtime、Domain、Action、Guard、Handoff与Persistence职责
- 适用范围：PCE-ERP全部运行代码和数据链
- 优先级：高
- 关联规范：03业务流程运行、04页面与交互、05自动验收、06模块专项
- 维护方式：持续更新

## 1. 标准运行链

```text
Page
  -> Schema
  -> Provider
  -> Runtime
  -> Domain
  -> Persistence
```

写动作同时受以下控制链约束：

```text
User Intent -> Action -> Guard -> Domain Transition -> Persistence
            -> Audit -> Handoff -> Downstream Provider
```

页面只呈现事实并提交意图；Schema定义数据形状；Provider提供权威事实；Runtime组织运行上下文；Domain负责业务规则与状态变化；Persistence负责持久化与并发一致性。

## 2. 职责唯一性

| 构件 | 唯一职责 | 禁止事项 |
|---|---|---|
| Page | 展示、输入、动作申请、反馈 | 重算业务事实、直接写状态、绕过Guard |
| Schema | 字段、类型、必填、枚举、关系 | 执行业务动作 |
| Provider | 从权威来源读取/适配事实 | 默认注入Demo、混用模式、页面缓存补齐 |
| Runtime | 组合上下文、会话与可观测状态 | 成为第二持久层、暗中推进状态 |
| Domain | 校验规则、计算决策条件、执行状态迁移 | 依赖页面DOM或路由临时参数 |
| Action | 表达业务动作申请、权限和幂等键 | 直接代表状态成功 |
| Guard | 在状态、数据、权限、完整性不满足时阻断 | 自动补数据后放行 |
| Handoff | 定义上下游对象、编号、版本和证据映射 | 只跳Route、不形成上下文 |
| Persistence | 事务、唯一性、锁、审计持久化 | 接受未经Domain/Guard验证的写入 |
| Acceptance | 证明对象、规则、动作、边界和结果 | 替代Domain或业务决定 |

原则必须明确：**Domain负责状态变化，Action负责业务动作申请，Guard负责阻断，Acceptance负责证明。**

## 3. State与Approval

- 状态码、标签、允许迁移、终态、回退、并发和审计必须由Domain/State Contract声明。
- 用户页面只显示服务端`statusLabel`；`statusCode`仅用于内部治理、筛选与协议。
- 禁止组件直接赋值状态；所有迁移必须经过Action和Guard。
- Approval配置、策略、实例、任务、结果和业务回写必须可追溯绑定；配置页面不是审批执行节点。
- 审批人员、角色、顺序、分离要求和终态含义由模块专项冻结；“审批完成”不自动等于执行外部动作。

## 4. Action与Guard契约

每个Action至少声明：`actionCode`、业务名称、允许状态、必需数据、权限、幂等键、成功结果、失败原因、审计字段和禁止副作用。

Guard必须同时检查：

1. 当前对象和版本存在；
2. 状态允许；
3. 必需字段和关联事实完整；
4. 用户、角色和数据权限满足；
5. 批量完整性满足；
6. 下游隔离和模块边界满足；
7. 重复提交不会重复产生业务结果。

按钮隐藏或禁用不能替代服务端Guard；事件入口和API必须再次校验。

## 5. Provider与事实所有权

- Production只读服务端Canonical事实或经审批的受控事实层；Canary和Demo必须显式隔离。
- API、页面、复制诊断、`strictFacts`和验收报告必须复用同一服务端事实。
- 数据存在但读取失败必须返回`read_failed`，不得伪装成`resultCount=0`。
- Provider返回来源、模式、数量、业务键、加载状态和错误契约；不得用上一页缓存、localStorage或前端重算补齐。
- 可观测性注册必须使用实例所有权；旧页面卸载不得清除新页面提供者。

## 6. Handoff与Route Context

- 上游动作必须形成持久或受治理Handoff，包含来源对象、来源编号、目标对象、版本、映射、证据和创建人/时间。
- 下游Provider优先读取真实Handoff，再读取受治理Runtime；Production禁止回退到Demo事实。
- Route只表达稳定页面身份，禁止携带订单号、物料编码、组合批次、ContextId、RuntimeContextId或Provider参数。
- 页面按`Route -> Context Resolver -> Task -> Business Object -> Provider -> Page Data`恢复。
- 上下文缺失、过期、越权或冲突必须阻断，禁止打开默认或空白业务实例。

## 7. 数据连续性

- 升级前冻结对象数量、业务键、来源关系、下游引用和数据Hash；升级后及刷新必须匹配。
- 已产生下游影响的事实禁止因页面重构、Provider切换或缓存清理丢失。
- Legacy事实必须标记来源和可信等级；不得冒充Production，不得补造缺失上游对象。
- 迁移必须单独审批、逐对象核验并可回滚；验收脚本不得制造正式业务数据。

## 8. 业务增强边界

业务增强默认只允许修改Domain、兼容Provider和目标页面业务区域。List Runtime、Page Shell、Process Center、公共组件、共享Router和跨模块状态机属于平台资产；修改它们必须升级为平台治理任务，完成影响分析、公共回归和人工验收。

Finance、WMS、MES、SCM等模块对象不得因相邻流程自动创建。付款、银行发送、库存、生产、采购订单等危险写入必须独立授权，默认关闭。

## 9. Runtime与Persistence安全

- Runtime对象不是交易对象，不得因存在于内存或浏览器而被视为持久事实。
- 写入必须分类为准备写、业务推进写、外部副作用写；验收必须分别计数。
- 外部网络、证书、生产密钥、真实发送、付款和订单创建默认禁止。
- Persistence写入必须事务化、校验唯一键、记录Actor/At/Before/After/Reason，并由API返回真实写入结果。

## 10. DATA-PROTECTION-001 人工数据不可变保护规则

### 10.1 适用范围

本规则保护所有已经由用户明确产生或确认的数据，包括：

- 人工录入数据；
- 人工确认数据；
- 人工选择结果；
- 人工审核意见；
- 人工调整结果。

### 10.2 核心原则

人工数据形成后，系统自动运行不得改变其值、语义、版本或归属。禁止：

1. 自动计算、后台同步或初始化逻辑覆盖人工数据；
2. 页面刷新覆盖尚在受治理编辑上下文中或已经保存的人工输入；
3. Provider重新加载覆盖人工确认数据；
4. Runtime同步、上下文恢复或缓存协调覆盖人工调整结果；
5. 流程跳转、页面重入或Handoff恢复使人工结果回到默认值；
6. 用空值、默认值、旧版本、系统建议值或重新计算值隐式替代人工结果。

发生版本冲突、来源冲突或人工数据无法恢复时，必须返回明确冲突或`read_failed/UNKNOWN`状态并阻断后续动作，禁止静默采用系统值。

### 10.3 数据优先级

统一数据优先级为：

```text
人工决策数据 > 系统计算数据 > 默认初始化数据
```

人工决策数据包括人工录入、选择、确认、审核和调整的结果。系统计算只能提供证据、建议或待确认值，不得反向成为人工决定。默认初始化数据仅在没有人工数据且没有系统计算事实时使用。

### 10.4 数据修改规则

人工数据只能通过明确Action修改，例如：确认、撤回、修改、重新提交。Action必须声明目标对象、允许状态、操作者、修改原因、版本、Before/After、发生时间、Guard和审计证据。

禁止页面赋值、Provider合并、Runtime同步、刷新回填、流程跳转或默认初始化构成隐式修改。撤回或重新提交不得删除历史人工版本；新结果必须形成可追溯版本并保留原结果。

### 10.5 模块适用

本规则适用于所有涉及人工决策的业务，至少包括：SCM供应商选择、Finance财务审核、MES生产异常处理、QMS质量判定。模块专项可以增加更严格的状态、权限和审计要求，但不得降低人工数据优先级或不可变保护。

## 11. DATA-IDENTITY-001 业务对象身份规范

### 11.1 身份三分法

所有业务对象、运行上下文、Gate、Handoff和交易聚合必须显式区分：

1. `ObjectId`：系统内部唯一且稳定的对象标识，用于持久化、关联、幂等和审计，例如`GATE-ID-202608080001`；
2. `BusinessNo`：面向业务用户的展示编号，例如`POG202608080001`，不得承担集合编码或关系解析职责；
3. `SourceRelations`：结构化来源关系，使用具有业务语义的单值或数组字段保存，例如`purchaseRequestIds[]`、`sourceObjectIds[]`及关系类型。

三者必须分别定义字段、唯一性、生成责任、展示责任和传递责任。一个值不得同时冒充系统标识、业务编号和来源集合。

### 11.2 多来源身份

一个对象关联多个采购申请、供应商、物料或来源单据时，必须保留稳定的自身`ObjectId/BusinessNo`，并通过`SourceRelations`完整保存全部来源。禁止把多个业务编号拼接成新编号，例如`GATE-PR001-PR002-PR003`；该字符串不可稳定解析，也无法表达顺序、版本和关系类型。

正确结构示例：

```text
ObjectId: GATE-ID-202608080001
BusinessNo: GATE001
SourceRelations:
  purchaseRequestIds: [PR001, PR002, PR003]
```

### 11.3 传递、展示与验收

- Schema、Provider、Runtime、Action、Handoff和Persistence必须保持相同身份语义，不得在层间改名、拼接、截断或用数组第一项替代对象身份；
- 页面显示`BusinessNo`及适用的完整来源关系，技术`ObjectId`仅在诊断、审计或明确需要时显示；
- 拆分、合并和批量处理必须保留原对象身份与关系类型，不得通过生成组合编号丢失来源；
- 验收必须分别验证对象唯一性、业务编号稳定性、来源关系数量和逐项匹配；任一身份缺失、冲突或不可解析时输出`FAIL/UNKNOWN`并阻断写动作。
