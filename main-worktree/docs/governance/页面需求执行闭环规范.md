# 页面需求执行闭环规范

- 规则编号：`REQUIREMENT-COMPLETENESS-001`
- 生效版本：`V1.14.2.8.4.27.2.9`
- 适用范围：PCE-ERP全部页面新增、修复与重构需求
- 状态：长期有效

## 1. 目的

页面交付必须证明需求在真实页面落地。源码存在、自动扫描或单独输出`PASS`均不能替代运行和操作证据。

## 2. 强制闭环

每项页面需求必须形成以下一一对应关系：

```text
Requirement ID
↓
Implementation File
↓
Runtime Component
↓
Browser Verification
↓
Acceptance Result
```

验收报告必须逐项记录需求名称、实现文件、真实URL、稳定页面定位、用户动作、可观察结果和证据文件。任一环节缺失时，该需求为`UNKNOWN`并阻断READY。

## 3. BUSINESS-DATA-VIEW-001 当前业务对象数据检查

页面显示的数据必须来自当前业务对象及其受治理子对象。浏览器验收必须同时检查页面业务编号、当前父对象身份、Provider过滤数量和实际渲染数量；仅验证Provider返回值而不检查页面DOM为FAIL。缓存、测试数据、上一页数据及其他父对象子项不得进入页面。

## 4. BROWSER-ACTION-001 真实按钮动作检查

按钮验收必须覆盖：按钮在真实URL可见、真实点击事件发生、声明的Handler被调用、运行层或Provider实际执行、结果在页面可观察。只验证按钮文本、源码绑定或模拟时间戳变化为FAIL。刷新、下载、打印等只读动作还必须证明URL和当前业务对象保持、业务写入为0。

## 5. 证据格式

| Requirement ID | 需求 | 实现文件 | Runtime Component | 浏览器动作与结果 | Acceptance Result |
| --- | --- | --- | --- | --- | --- |
| `<id>` | `<需求>` | `<path>` | `<component>` | `<URL / action / observable result>` | `PASS/FAIL/UNKNOWN` |

禁止只输出无证据的`PASS`。证据必须归档至`frontend/test-results`，并遵守`PAGE-RUNTIME-001`、`PROCESS-009`与`CODEX-EVIDENCE-001`。

## 6. 完成条件

- 全部Requirement ID均有实现、Runtime、真实浏览器和结果证据；
- 页面数据与当前业务对象一致；
- 所有声明按钮均完成真实点击；
- 业务写入与禁止边界符合任务要求；
- 自动验收、真实浏览器验收和Build全部通过。

## 7. 真实页面优先原则

页面需求的判定顺序固定为：

```text
Browser DOM
↓
User Click
↓
Runtime State
↓
Provider Data
```

上层失败时，下层PASS不得覆盖。禁止使用Provider PASS、Mock Data、Test Data、时间戳变化或测试脚本中的固定数量替代真实页面结果。人工真实页面FAIL时必须执行`CODEX-COMMAND-002`，原自动PASS立即失效。

## 8. BROWSER-DOM-001 真实DOM验收

验收必须从目标URL的实际DOM读取用户可见控件、标签、值、表格业务行和动作结果。下拉框必须真实展开并读取选项；表格必须用稳定业务行标识统计，不得把表头、空态、展开行或其他区域计入；刷新必须记录点击事件、Provider调用和DOM提交三个独立结果。浏览器DOM结果与报告数量不一致时一律FAIL。

## 9. REAL-BUSINESS-DATA-001 真实业务数据来源

页面事实必须从当前路由业务对象经受治理Provider读取。采购订单详情明细只能沿`PurchaseOrder.id → PurchaseOrderItem.purchaseOrderId → Items → DOM`正向提取；禁止从Gate、采购申请、询价、报价比较反向聚合，禁止使用测试数组、Demo回退或上一页缓存补齐。

## 10. DOM-BUSINESS-MATCH-001 DOM与业务对象一致性

真实浏览器验收必须同时记录当前父对象ID、Provider子项数量、Provider子项业务编码、DOM业务行数量和DOM业务编码。父子归属、数量或编码集合任一不一致即为FAIL；排序差异必须先按业务明细顺序规范化后再比较，禁止只比较固定数量。

## 11. NUMBER-CANONICAL-001 正式业务编号唯一来源

采购订单页面只能显示一个“采购订单编号”，其值必须原样来自`PurchaseOrder.objectNo`或已声明的正式业务编号字段。禁止把Gate、采购申请、询价、报价或多个来源编号拼接成采购订单编号，禁止前端生成编号，禁止以“PO编号”等同义字段形成重复业务身份。

## 12. PURCHASE-ORDER-NUMBER-SOURCE-001 与 PURCHASE-ORDER-ITEM-OWNERSHIP-001

- `PURCHASE-ORDER-NUMBER-SOURCE-001`：验收必须输出正式编号值与实际字段名，并证明页面值逐字等于当前PurchaseOrder事实。
- `PURCHASE-ORDER-ITEM-OWNERSHIP-001`：每条渲染明细必须携带并匹配当前`PurchaseOrder.id`对应的`purchaseOrderId`；缺失、冲突或属于其他订单的行必须拒绝。
- `TEMPLATE-SCHEMA-MATCH-001`：导入模板字段必须由PurchaseOrder Schema生成，系统生成的采购订单编号、状态、创建时间不得成为导入列；模板必须包含业务数据页和字段说明页。

## 13. PURCHASE-ORDER-NUMBER-SOURCE-CHECK-002 采购订单编号来源检测

- canonical字段固定为`PurchaseOrder.objectNo`；`purchaseOrderNo`与`poNo`仅作为兼容别名，不得成为页面第二来源；
- 列表、详情、打印和导出显示值必须逐字等于当前PurchaseOrder事实的`objectNo`；
- 页面显示编号禁止包含`PAP-PI`、`QC-PI`、`Gate`、`Source Chain`或其他来源链片段；
- 来源Gate编号必须保留在独立追溯字段，禁止与采购订单编号合并；
- 任一消费端读取兼容别名、重算或拼接编号时，本规则为FAIL并阻断READY。

## 14. PURCHASE-ORDER-NUMBER-PURITY-001 编号纯度门禁

- 唯一读取入口为`getPurchaseOrderNumber(order)`，且该函数只能原样返回`order.objectNo`；
- 列表、详情、打印、导出、搜索和排序必须调用该入口，禁止直接读取兼容别名或来源字段；
- 正式编号禁止包含`PAP-PI`、`PI-`、`QC-`、`PAP-`、`Gate`；
- 来源链只能进入独立追溯字段，不得进入采购订单编号、搜索编号或排序编号；
- 任一正式编号命中禁止片段时必须显式FAIL，禁止使用formatter、adapter或页面替换修复污染值。
