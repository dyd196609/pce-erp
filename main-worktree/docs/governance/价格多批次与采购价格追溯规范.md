# 价格多批次与采购价格追溯规范

## 1. 目的

本规范定义 SupplierMaterialPrice（供应商物料价格）的多批次版本、当前适用价格、历史价格、编辑边界与采购订单快照追溯。所有消费者必须复用服务端价格事实，禁止页面缓存、前端重算或另一套价格表补齐。

## 2. 身份与适用范围

每条正式价格以 SupplierMaterialPrice 数据库 ID 和 `priceNo` 标识。版本分组键必须由服务端明确返回。

当前模型的默认分组键：

`supplierCode + materialCode + currency + DEFAULT`

`DEFAULT` 表示模型尚未表达更细的适用范围，不代表所有未来场景天然相同。增加采购组织、工厂、地点、计量单位、数量阶梯或贸易条款时，必须先扩展持久化模型和服务端 `scopeDimensions`，再纳入 `scopeKey`；禁止页面私自拼接或猜测维度。

## 3. 版本状态

服务端对同 scope 的正式价格按确认时间、创建时间和稳定业务编号排序，并返回：

- `CURRENT`：当前日期有效，且为该 scope 确定性排序后的当前适用版本。
- `HISTORICAL`：保留的较早版本或已经失效的正式版本。
- `FUTURE`：尚未到生效日期。
- `DISABLED`：非启用正式状态。

每条记录还必须返回 `versionNo`、`isCurrentApplicable`、前后版本编号以及重叠分类。多个有效期重叠记录可以被归类为历史版本关系，但不可被静默删除、覆盖或全部显示成“当前有效”。

## 4. 单价与维护边界

- 正式单价一经确认，不允许在通用维护弹窗直接覆盖。
- 单价变化必须经价格确认流程创建新的 SupplierMaterialPrice 版本。
- 通用维护入口仅允许更新税率、生效日期、失效日期与强制修改原因。
- 每次更新必须记录修改人、修改时间、原因和所有字段的新旧值。
- 请求携带不同 `unitPrice` 时，服务端必须拒绝并返回稳定错误码。
- 保存成功后，页面必须从服务端重新加载，不得仅修改本地行数据冒充持久化。

## 5. 来源链

每条正式价格必须可追溯：

`SupplierMaterialPrice -> PriceApprovalResult -> originalSourceType + originalSourceReference`

来源可以是 SupplierQuotation（供应商报价）或经治理确认的历史事实，但不得填写无法定位的描述性文本代替业务身份。页面、API、strictFacts（严格事实）和验收报告必须展示同一来源链。

## 6. 采购订单快照

采购订单项目必须同时保存：

- `supplierMaterialPriceId`
- `priceApprovalResultId`
- `unitPriceSnapshot`
- `taxRateSnapshot`
- `currencySnapshot`
- 必要的物料身份快照

后续新增价格版本不得反向修改历史采购订单快照。追溯时以订单项目记录的价格身份和快照解释“当时为什么使用该价格”，不能用当前价格覆盖历史事实。

## 7. 查询与选择契约

价格事实接口可按 `supplierCode`、`materialCode`、`currency` 精确查询，并返回全部候选版本与服务端判定状态。

查询接口是只读能力：

- 不自动创建采购订单。
- 不按返回顺序默认第一条。
- 不在缺失 scope 维度时猜测。
- 不把历史版本抹除后只返回当前行。
- 不允许调用方前端重新定义“当前适用”。

标准采购自动选价属于独立增量批次，必须在明确错误码、冲突阻断、无适用价格阻断和人工改价权限完成后接入。

## 8. 下游追溯边界

收货、入库、结算和成本核算应从 PurchaseOrderItem（采购订单项目）携带的价格身份向上追溯，不应重新按当前日期选价。建设追溯字段不授权创建或推进任何下游单据，也不授权付款、银行发送或总账写入。

## 9. 最低验收证据

每次版本治理至少证明：

1. 同 scope 多个真实价格版本同时存在且身份唯一。
2. 服务端能区分当前、历史、未来和停用状态。
3. 每个版本能追溯确认结果与原始来源。
4. 允许字段修改在页面刷新后仍存在，并有新旧值审计。
5. 正式单价直接覆盖被阻断。
6. 采购订单保留其生成时的价格 ID 和价格快照。
7. 自动门禁、后端测试、真实浏览器证据和人工验收状态分别报告。
