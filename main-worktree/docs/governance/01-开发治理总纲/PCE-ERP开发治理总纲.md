# PCE-ERP开发治理总纲

# 文档信息

- 版本：V1.14.2.8.4.27.2.36
- 用途：PCE-ERP软件开发治理的唯一最高入口
- 适用范围：PCE-ERP全部模块、代码、页面、流程、数据、验收与治理任务
- 优先级：高
- 关联规范：PCE-ERP智能化开发总纲、02架构与运行边界、03业务流程运行、04页面与交互、05自动验收、06模块专项、07案例库
- 维护方式：持续更新
- 治理角色：唯一最高治理入口

## 1. 软件定位

PCE-ERP是以服务端事实、受治理业务对象、显式状态机、人工决策边界和可重放证据为基础的企业管理软件。开发目标不是“页面存在”或“脚本通过”，而是业务对象、运行链、用户动作、边界保护和证据同时成立。

## 2. 治理层级与唯一入口

治理读取顺序固定为：

```text
01 开发治理总纲
  -> PCE-ERP智能化开发总纲（全部开发任务强制读取）
  -> 02 架构与运行边界规范
  -> 03 业务流程运行治理规范
  -> 04 页面与交互开发规范（页面任务适用）
  -> 05 自动验收与证据治理规范
  -> 真实运行验收规范（全部含页面或可运行入口的任务强制读取）
  -> 06 对应模块专项治理规范
  -> 07 问题案例库
```

本文件是唯一最高入口。《PCE-ERP智能化开发总纲》是本总纲下的强制专项总纲，负责已有智能能力优先与禁止重复框架治理，不构成第二个最高入口。其他文件只能细化下游规则，不得再次声明最高优先级、另一套读取顺序或覆盖总纲。历史文件位于`archive`，仅用于追溯，不作为默认开发入口。

## 3. 基本开发原则

1. `GOV-001`：先规范、后设计、再开发、最后验收。
2. 权威事实优先：API、Provider、Runtime、页面、诊断和验收必须读取同一事实，不得用页面缓存或前端重算补齐。
3. 人工决策边界：证据不等于决定；禁止自动审批、自动推荐、自动生成下游交易对象，除非模块专项和独立权限契约明确授权。
4. 最小修改：只修改任务授权范围，保留用户已有变更，禁止通过公共组件修复单页业务问题。
5. 数据连续性：升级前后、刷新和重新进入必须保持业务对象数量、业务键、来源关系与下游引用。
6. 失败显式：缺少证据为`UNKNOWN`，检查失败为`FAIL`；不得用默认值、空集合或构建成功冒充业务通过。
7. 历史可追溯：规范、案例、验收和冻结版本不得无记录删除或覆盖。
8. 人工优先原则：人工确认结果的优先级高于系统计算结果，系统计算结果的优先级高于默认规则结果。系统自动运行、刷新、Provider重载、Runtime同步、流程跳转和页面重入均不得隐式覆盖人工数据；人工数据只能经明确Action修改。
9. 运行资产不可随意变化原则：已经完成专项验收并签发READY的页面结构、交互结构、流程可视化和公共运行契约均属于已验收运行资产。后续版本不得因相邻业务开发、公共组件调整、样式整理或验收脚本改写而静默改变；修改前必须识别冻结资产、输出影响分析，并由专项版本完成回归与重新验收。
10. 真实运行验收优先原则：代码通过不等于系统通过，自动验收通过不等于页面真实可用。存在页面或可运行入口的任务必须同时取得自动验收、真实浏览器人工验收与Build证据；三者任一为`FAIL`或`UNKNOWN`时禁止签发READY。

人工优先原则适用于全部人工决策场景，包括SCM供应商选择、Finance财务审核、MES生产异常处理、QMS质量判定以及其他模块的人工录入、选择、确认、调整和审核结果。

## 4. Codex执行原则

### 4.1 任务身份

每项任务必须声明版本、类型、主题、目标、允许范围、禁止范围和最终状态。复合任务必须标出主任务类型。

### 4.2 开发前读取

Codex必须按第2节顺序读取适用规范，并输出实际加载结果。缺失、为空或读取失败时，`Governance PASS`必须为FAIL。

### 4.3 强制执行链

```text
任务身份 -> 治理加载 -> 智能化影响评估 -> 已有能力扫描 -> 复用方案 -> 实施边界
-> 历史案例 -> 边界冻结 -> 现状扫描
-> 规则设计 -> 实施 -> 自动验收 -> 真实浏览器人工验收 -> READY三重门禁 -> 案例闭环 -> 最终报告
```

任何未来版本，无论是否直接开发智能功能，都必须在实施前输出“智能化影响评估、已有能力扫描、复用方案、实施边界”。存在适用的Schema、Registry、Runtime、Provider、公共组件或配置能力时必须优先复用；无法证明现有能力不适用时，禁止新建平行Metadata、Runtime、Registry、Schema或Config体系。

### 4.4 CODEX-COMMAND规则

- `CODEX-COMMAND-001`：报告必须包含治理映射、修改文件、验收矩阵、失败阻断和最终状态。
- `CODEX-COMMAND-002`：自动PASS不能覆盖人工FAIL；出现该组合时状态为`AUTO_PASS_HUMAN_FAIL`并阻断READY。
- `CODEX-COMMAND-003`：必要治理更新未完成前禁止进入业务实现。
- `CODEX-COMMAND-004`：READY只能由`Automatic Acceptance=PASS`、`Browser Human Acceptance=PASS`、`Build=PASS`共同产生；缺少截图或页面字段化证据时人工验收为`UNKNOWN`。

### 4.5 Codex治理检查模板

所有Codex实施任务除任务专属结果外，必须显式输出以下治理检查；不适用项填写`N/A`及原因，禁止省略：

```text
Governance Files Loaded: PASS/FAIL
Frozen Asset Check: PASS/FAIL/N/A
Identity Check: PASS/FAIL/N/A
Data Extract Check: PASS/FAIL/N/A
Array Completeness: PASS/FAIL/N/A
Regression Check: PASS/FAIL/N/A
Automatic Acceptance: PASS/FAIL
Browser Human Acceptance: PASS/FAIL/N/A
Build: PASS/FAIL
Ready Gate: PASS/FAIL
```

- `Frozen Asset Check`必须映射`PAGE-RUNTIME-FREEZE-001`、`FLOW-VISUAL-FREEZE-001`及受影响公共组件；
- `Identity Check`必须验证`ObjectId`、`BusinessNo`与`SourceRelations`职责分离；
- `Data Extract Check`必须验证Provider、Runtime、Action和Adapter没有单条降维；
- `Array Completeness`必须记录集合输入、输出和来源关系数量；
- `Regression Check`必须覆盖已验收资产、影响页面和既有Golden Path。

## 6. 版本管理

- 治理变更必须记录版本、原因、范围、替代关系和验证结果。
- 规则只能追加、明确替代或归档；禁止静默删除。
- 模块专项不得降低核心规则；冲突时执行总纲和核心规范中更严格的边界。
- 每次READY必须对应可重放的自动证据与适用的人工证据。

## 7. 修改边界原则

任务执行前必须冻结文件与数据基线。只读分析不授权写入；页面修复不授权修改Domain；业务增强不授权修改List Runtime、Page Shell、Process Center或公共组件；治理任务不授权修改业务代码、数据库或生产数据。

需要扩大范围时必须停止并取得新授权。任何删除、迁移、状态推进、外部发送、付款或订单创建都必须由任务明确授权和独立Guard保护。

## 8. 完成定义

任务只有在规范映射、架构边界、业务规则、Guard、自动验收、真实浏览器人工验收、截图证据、数据保护和Build适用项均有证据时才可READY。无页面或可运行入口的纯文档任务可以将`Browser Human Acceptance`标记为`N/A`，但必须说明原因且不得用N/A掩盖可访问页面；其余任务三项门禁必须全部为PASS。最终报告统一引用05规范和《真实运行验收规范》的输出格式；存在FAIL或UNKNOWN时必须输出失败状态。
