1. “确认报价”动作定义：`frontend/src/meta/process/scm/scmUnifiedListActionContractsV1142813.js`。
2. 注册来源：现有 SCM 统一列表动作 Registry/Metadata；页面不再自建第二套动作数组。
3. 可见性计算：`frontend/src/meta/runtime/listActionColumnRuntime.js` 按当前行执行 `visibleWhen`；服务端在 `backend/masterdata/master_data_statistics_runtime.py` 输出逐对象 `actionAvailability`。

5. 原按钮全部消失的直接原因：页面局部动作元数据与中央动作 Registry 发生漂移，同时当前 22 条数据本身没有满足全部归档条件的对象。不是 4 条映射失败导致全局过滤。
6. 根因分类：Metadata 丢失/漂移 + 当前逐对象归档事实均不可确认。`archiveStatus` 与数据库持久化事实未发现全局判断错误。

8. 不应显示的记录：16 条已归档、4 条映射待处理、1 条未完成、1 条未通过。

重点排除结果：不存在 `SupplierMaterialPrice Count > 0` 或“任一对象已归档即全局隐藏”的逻辑；判断按 PriceApprovalResult/正式 sourceReference 逐对象执行。历史 `sessionConfirmed` 等兼容数据不参与正式数据库归档状态权威判断。

## PCE List Refresh Capability Scan（统一列表刷新能力扫描）

扫描发现公共表格此前只有搜索、筛选、排序等契约，没有统一的页内 Provider 刷新入口；供应商物料价格等页面存在局部刷新实现，部分页面只依赖公共页面壳刷新，形成多种实现。

本次在现有 `pceEnterpriseListContract.js` 上扩展 `LIST-REFRESH-CONTRACT-001`，没有创建第二套 List Runtime。标准流程为：Registry Provider 强制重新取数 → 替换 rows → 复用现有筛选/排序/分页 Runtime → 更新结果数/总数 → 中文反馈。禁止整页 reload。

已验证：

- 供应商物料价格：公共工具栏仅 1 个刷新入口；实际调用正式 Runtime Provider；刷新后搜索条件和 1 条结果保持；总数仍为服务端 16。
- 物料供应商关系：公共刷新入口和“数据已刷新”反馈有效。
- 物料、供应商、工艺路线：现有 `PceListPageShell` 可调用各自注册的服务端 Provider；页面显示 API 与服务端总数。
- 员工、工序、设备：现有页面仅有本地 Foundation Store Provider，缺少服务端事实 Provider；本版本不伪造网络刷新，列为后续治理缺口。
- 供应商价格事实：独立受治理事实页，不修改 SupplierPriceFact；未将其接入价格归档写链。
